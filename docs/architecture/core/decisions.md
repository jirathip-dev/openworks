# Decisions

The core's numbered decisions, a line or two each. Shapes: [`shapes.md`](shapes.md). Statecharts: [`statecharts.md`](statecharts.md).

1. **One repo, four crates, one npm package, one version.** `openworks-core` (pure rules: no database, HTTP, runtime, trade or country), `openworks-db` (queries and migrations), `openworks` (what a host depends on: the host trait, the pack interface, the operations, the declarations, prints) and `openworks-server` (the standalone binary), plus `openworks-web` (the generated client, the default screens and `mount()`). An example pack lives in the repo only to prove the pack interface in CI; the host trait, declaration macros, events and hooks are written here, not shared with another product as a crate.
2. **Plain tables, a company id on every row, rules in Rust.** Schema `works`; every table has `org_id` and every foreign key includes it. No RLS: isolation is in code, held by the compiled-query test. The database keeps tables, constraints and two guards (an approved report or job order does not change; a job number is never reused). Ids are UUIDv7; a row a host also knows by its own id carries `host_ref`.
3. **Hours and days, never money.** No price, rate, cost, currency or contract value is stored in `works`; money belongs to another product or to a pack. A test over the migrations fails a money-named column and an arch ban keeps the words out of the code; money beside a job on a screen is a pack's slot.
4. **The spine: client, site, project, job, task.** A host's existing project record maps one to one onto a project, with a job beside it. A client is a name a host fills by `host_ref`; a site is a place under a client; a project holds a stage, its people and an optional parent with a link kind; a job holds its windows, calendar, actual dates, status and a number once it opens (its first job is created proposed with the project, and winning opens and numbers it); a task is a unit of planned work in a job. Stages are the company's own list with one of four fixed kinds (open, won, done, lost), and the rules run on the kind only; lost reasons are the company's list too.
5. **Members are core; a host narrows what they may do.** `works.members` with four fixed roles (Owner, Manager, Member, Viewer) and `works.project_members` with roles from the company's own list. A caller is scoped to all projects or their own. A host may narrow, never widen: through the scope it reports and a reach it attaches to each operation where it mounts the router.
6. **Every operation is declared once; only a person commits.** `read!`, `write!` or `closed!` on every route, so a route is also a screen action and an assistant tool. A read is a tool, a write is a proposal a person confirms, and a delete, members and setup, or approving as someone else are never a tool.
7. **Events, hooks, extension data, approval kinds.** Every change writes one row to `works.events`; a pack hooks in with `before_commit` (refuse, or write its own rows beside the change) and `after_commit` per event, retried; `run_due(now)` runs background work, and the core has no clock or thread. Extension data is the pack's own tables keyed by the core's id, attached to reads under `ext.<key>` (no JSON bag, no custom-field engine). Approvals are one engine: the core owns job-order and daily-report approval, and a pack adds kinds on its own subjects that share the inbox, signature and decision rule.
8. **Default screens in the product; a host may keep its own.** `openworks-web` ships default Blocks screens for a standalone install, drawn by a design lane first. `mount()` has slots: a host replaces a whole destination or adds panels, flags, cards and tabs inside a default one, and a host that keeps its own screens takes only the typed client.
9. **How a host takes it in.** Exact pins of the crates and the npm package, all equal; the pinned version's migrations are vendored into the host's own migration chain; no client role has a grant on `works`; the host reaches it inside the caller's transaction; `openworks::check()` refuses to serve when the schema is behind. openworks depends on no other product, and no other product's name appears in it.
10. **A host moves slice by slice, by a switch.** A host replacing its own tables moves each slice through off, mirror (its tables are the truth, each write also applied to `works` and differences logged) and on (`works` is the truth, its old columns kept as a copy in the same transaction), and back without loss; a slice closes when no reader of a copied column is left. That switch is the host's own; the core only needs every write to come through its operations.
11. **Order.** Spine, planner, crew and equipment, daily reports, job orders and approvals, Today. Each slice is core issues that end in a release; a host's adoption follows each release.
12. **CI and the quality bar.** GitHub-hosted runners only; gatekeeper packs core, rust and ts with every gate blocking; tests against Postgres; the org-scope test; the public-surface diff; the Blocks guard with 390 and 1440 screenshots. Three gates are this product's own: the no-money test, the neutral-words ban (no trade or country word in the core), and the suite run with no pack installed.
